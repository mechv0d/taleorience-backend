## 2.1. Domain rules

Нельзя:

```text
domain зависит от NestJS
domain зависит от HTTP
domain зависит от Drizzle
domain хранит UI strings
domain хранит глубокие копии entities
domain использует arrays of embedded entities вместо IDs
```

Нужно:

```text
domain использует GUID
domain использует Result
domain генерирует domain events
domain соблюдает invariants
```

---

## 2.2. Application rules

Нельзя:

```text
use-case напрямую пишет SQL
use-case знает про Fastify request
use-case возвращает HTTP status
use-case мутирует чужие collections без repository
```

Нужно:

```text
use-case использует repository interfaces
use-case использует UnitOfWork
use-case возвращает domain result
use-case проверяет permissions и project scope
```

---

## 2.3. HTTP rules

Нельзя:

```text
controller содержит бизнес-логику
controller напрямую ходит в repository
controller возвращает internal DB rows
controller использует hardcoded error messages
```

Нужно:

```text
controller вызывает use-case
controller использует Zod DTO
controller возвращает problem+json errors
controller использует presenters
```

---

## 2.4. Localization rules

Нельзя:

```ts
throw new NotFoundException('Project not found');
```

Правильно:

```ts
throw new DomainError({
  code: 'PROJECT_NOT_FOUND',
  messageKey: 'errors.projectNotFound',
  params: { projectId }
});
```

Нельзя хранить системные строки в domain:

```ts
template.name = 'Character';
```

Лучше:

```ts
template.titleKey = 'template.character.title';
```

---

## 2.5. Persistence rules

Нельзя:

```text
хранить pages как nested JSON inside game_objects
хранить blocks как nested JSON inside pages
хранить assets внутри blocks
хранить templates как live-linked parent objects
```

Нужно:

```text
flat tables
GUID primary keys
projectId scoping
foreign keys by ID
JSON only for block data / template blueprint
```

# 7. Multi-client readiness

Backend должен одинаково хорошо обслуживать:

```text
Web SaaS
Android App
Windows local/web
macOS local/web
Linux local/web
```

Для этого:

1. API versioned: `/api/v1`.
2. OpenAPI schema всегда актуальна.
3. Auth optional/local/pluggable.
4. Assets отдаются через endpoint, а не только через filesystem.
5. Large uploads поддерживают resumable mechanism позже.
6. Ошибки machine-readable.
7. Локализация не зашита в backend text.
8. Все операции идемпотентны там, где это критично.
9. Списки используют cursor pagination.
10. Events доступны через SSE/WebSocket для live UI.

# Техническая архитектура backend-only проекта TaleOrience / World Engine

Ниже — производственная backend-архитектура, рассчитанная на то, что позже с ней будут работать:

- web SaaS frontend;
- Android-приложение;
- локальный web-клиент на Windows / macOS / Linux;
- self-hosted deployment;
- будущий PWA/offline-клиент.

Backend проектируется как отдельный продукт: REST API + event channel, без привязки к конкретному клиенту.

---

## 0. Базовые архитектурные решения

### 0.1. Рекомендуемый стек

| Слой | Технология | Причина |
|---|---|---|
| Runtime | Node.js 22 LTS | Единый TypeScript-стек с frontend, хорошая экосистема |
| Language | TypeScript strict | Типобезопасность, лучшие DTO-контракты |
| HTTP framework | NestJS + Fastify adapter | Модульность, DI, guards, interceptors, удобная архитектура |
| Validation | Zod | Strict schema validation DTO, OpenAPI-friendly |
| ORM / SQL builder | Drizzle ORM | Поддержка SQLite и PostgreSQL, контроль SQL, migrations |
| Database local/self-hosted | SQLite | Простой local-first / self-hosted режим |
| Database SaaS | PostgreSQL | Multi-user, SaaS, production |
| Search | SQLite FTS5 / PostgreSQL full-text | Без Elasticsearch/Meilisearch на старте |
| File storage | Local FS adapter, позже S3-compatible | Self-hosted сначала простой |
| Events | In-memory event bus → SSE → WebSocket | Подготовка к collaboration без усложнения MVP |
| Logging | pino / nestjs-pino | Структурные логи |
| Testing | Vitest + Supertest | Быстрые unit/integration/e2e тесты |
| API docs | OpenAPI 3 via `@nestjs/swagger` | Генерация клиентов для web/Android/desktop |
| Package manager | pnpm workspaces | Монорепозиторий backend-пакетов |
| Container | Docker / Docker Compose | Self-hosted и SaaS deployment |

---

### 0.2. Ключевые архитектурные принципы

Backend обязан соблюдать правила из ТЗ:

1. **Domain layer не зависит от HTTP, React, UI, SQLite/PostgreSQL.**
2. **Application layer содержит use-cases / commands / queries.**
3. **Persistence — заменяемый adapter.**
4. **Все сущности имеют GUID / UUID.**
5. **Связи — через ID, без глубокой вложенности.**
6. **Project — корневая логическая граница данных.**
7. **Каждая сущность имеет `projectId`.**
8. **Templates — не live inheritance, а instantiation + deep copy + reference remapping.**
9. **Assets хранятся отдельно, Blocks только ссылаются на `assetId`.**
10. **Inspector metadata относится к GameObject, не к Page.**
11. **Системный текст — localization keys, пользовательский контент не переводится автоматически.**
12. **Ошибки API возвращают `messageKey`, а не hardcoded text.**

---

### 0.3. Режимы работы backend

Backend должен поддерживать несколько режимов через config:

```env
APP_MODE=local | self_hosted | saas
AUTH_MODE=none | local | saas
DATABASE_URL=sqlite://./data/taleorience.db | postgres://...
STORAGE_DRIVER=local | s3
DEFAULT_LOCALE=en
FALLBACK_LOCALE=en
```

Режимы:

| Режим | Описание |
|---|---|
| `local` | Локальный сервер для desktop/web, без обязательного аккаунта |
| `self_hosted` | Docker на Mac mini / LAN / VPS, SQLite или PostgreSQL |
| `saas` | Cloud, PostgreSQL, auth, billing, permissions, storage |

## 1.1.1. Общие API-соглашения

### Формат данных

Основной формат:

```http
Content-Type: application/json
```

Ошибки возвращаются как:

```http
Content-Type: application/problem+json
```

Пример ошибки:

```json
{
  "type": "https://taleorience.dev/errors/project-not-found",
  "code": "PROJECT_NOT_FOUND",
  "messageKey": "errors.projectNotFound",
  "params": {
    "projectId": "01955b3a-8d2f-7a1c-9f2e-3c1f4a2d9b10"
  }
}
```

`messageKey` нужен, чтобы клиент сам локализовал сообщение через:

```text
/system/locales/{locale}/{namespace}
```

---

### Пагинация

Для списков:

```http
GET /api/v1/projects?limit=50&cursor=...
```

Ответ:

```json
{
  "items": [],
  "nextCursor": "..."
}
```

Используется cursor-based пагинация, а не offset-based, потому что она стабильнее для больших миров.

---

### Локализация

Клиент может передавать:

```http
Accept-Language: ru
```

или:

```http
GET /api/v1/system/templates?locale=ru
```

Приоритет:

```text
query.locale > Accept-Language > DEFAULT_LOCALE
```

Важно:

- системные тексты возвращаются как `messageKey`, либо как вычисленное поле `displayName`, если клиент запросил локализацию;
- пользовательский контент не переводится автоматически.

---

### Идемпотентность

Для POST-операций рекомендуется заголовок:

```http
Idempotency-Key: 7f0d2f6a-1111-4a5b-9d0f-9d3a0c4a1b2c
```

Особенно важно для:

- создания проектов;
- загрузки assets;
- клонирования;
- импорта;
- instantiate template.

---

### Optimistic concurrency

Для обновлений можно использовать:

```http
If-Match: "version-42"
```

Если объект изменён параллельно:

```http
412 Precondition Failed
```

Это важно для будущего collaboration и Android-клиента.

## 1.1.15. Jobs / Async operations

Некоторые операции должны уметь быть асинхронными:

- export;
- import;
- clone project;
- copy large assets;
- reindex search.

| Метод | Путь | Назначение | Статус |
|---|---|---|---|
| GET | `/jobs/{jobId}` | Статус задачи | MVP/Later |
| POST | `/jobs/{jobId}/cancel` | Отмена | Later |
| GET | `/jobs/{jobId}/artifact` | Скачать результат, например export zip | Later |

Пример:

```http
POST /api/v1/projects/{projectId}/export
```

Ответ:

```json
{
  "jobId": "01955b3a-8d2f-7a1c-9f2e-3c1f4a2d9b10",
  "status": "queued"
}
```

## 1.1.17. Project content localization / translations

Это не обязательно для MVP, но архитектура должна это не ломать.

| Метод | Путь | Назначение | Статус |
|---|---|---|---|
| GET | `/projects/{projectId}/content-locales` | Доступные языки контента | Future |
| PUT | `/projects/{projectId}/content-locales/{locale}` | Включить язык | Future |
| GET | `/projects/{projectId}/pages/{pageId}/translations` | Переводы страницы | Future |
| PUT | `/projects/{projectId}/pages/{pageId}/translations/{locale}` | Сохранить перевод страницы | Future |

Важно:

- пользовательский markdown не переводится автоматически;
- переводы страниц — отдельный пользовательский контент;
- системные тексты проекта/шаблонов используют localization keys.

## 1.2.8. Правило зависимостей

Разрешено:

```text
api → application
api → contracts
application → domain
infrastructure → application
infrastructure → domain
api wiring → infrastructure
```

Запрещено:

```text
domain → application
domain → infrastructure
domain → api
application → infrastructure
application → api
controllers напрямую меняют collections
repository возвращают вложенные aggregate-документы без необходимости
```

Это нужно контролировать через:

- ESLint import boundaries;
- code review;
- архитектурные тесты;
- TypeScript paths.
