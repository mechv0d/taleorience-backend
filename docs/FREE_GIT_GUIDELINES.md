# Git workflow и управление версиями World Engine "TaleOrience"

## Общая философия

Git используется не только как место хранения кода, а как система
управления жизненным циклом продукта.

Основные цели:

-   стабильная разработка без страха ломать production;
-   понятная история изменений;
-   возможность быстро откатывать релизы;
-   отделение разработки от выпуска;
-   подготовка проекта к Open Source и SaaS-развитию.

------------------------------------------------------------------------

# Основные понятия

## Branch (ветка)

Ветка --- это изменяемый указатель на последовательность commit-ов.

Пример:

    main
     |
     ●──●──●──●

Новый commit двигает ветку вперёд.

------------------------------------------------------------------------

## Commit

Commit --- это зафиксированное состояние кода.

Каждый commit должен иметь понятное описание изменения.

Примеры:

    feat: add project cloning
    fix: repair asset import
    refactor: simplify repository layer
    test: add block serialization tests

------------------------------------------------------------------------

## Tag

Tag --- это фиксированная метка конкретного commit.

Версии вида:

    v0.1.0
    v0.2.0
    v1.0.0

являются tag-ами, а не ветками.

Пример:

    main

    ●──●──●──●──●
             |
           v0.4.0

Если после этого появятся новые commit-ы:

    main

    ●──●──●──●──●──●──●
             |
           v0.4.0

Tag остаётся на старом состоянии.

------------------------------------------------------------------------

# Версии

World Engine использует Semantic Versioning:

    MAJOR.MINOR.PATCH

Пример:

    v1.4.2

Где:

## MAJOR

Большие несовместимые изменения.

Пример:

    v1.0.0 → v2.0.0

Когда:

-   меняется API;
-   ломается формат данных;
-   требуется миграция проектов.

------------------------------------------------------------------------

## MINOR

Новая функциональность без поломки существующего.

Пример:

    v0.3.0 → v0.4.0

Когда добавлены:

-   новые Block types;
-   новые инструменты;
-   новые возможности редактора.

------------------------------------------------------------------------

## PATCH

Исправления.

Пример:

    v0.4.0 → v0.4.1

Когда:

-   исправлены баги;
-   улучшена стабильность;
-   исправлены ошибки без новых возможностей.

------------------------------------------------------------------------

# Рекомендуемая структура веток

Основные ветки:

    feature/*
          |
          v
         dev
          |
          v
        main
          |
          v
       release tag
          |
          v
     production

------------------------------------------------------------------------

# Dev branch

Назначение:

Активная разработка.

Пример:

    dev

В неё попадают:

-   новые функции;
-   эксперименты;
-   архитектурные изменения;
-   исправления.

Допускается:

-   временный плохой код;
-   недоделанные функции;
-   изменение API.

Но:

-   проект должен собираться;
-   нельзя оставлять полностью сломанное состояние.

Примеры:

    feat: add Tiptap integration
    feat: create Project Manager
    refactor: change entity storage

------------------------------------------------------------------------

# Feature branches

Для крупных изменений рекомендуется создавать отдельные ветки.

Примеры:

    feature/project-system
    feature/tiptap-editor
    feature/localization
    feature/cloud-sync

Работа:

    feature/project-system

           |
           |
           v

          dev

После завершения:

Pull Request → Review → Merge.

------------------------------------------------------------------------

# Main branch

Назначение:

Стабильная версия разработки.

В main попадает только проверенный код.

Перед merge:

-   проект собирается;
-   проходят unit tests;
-   проверяется архитектура;
-   исправляются warning;
-   выполняется code review.

Пример:

    dev
     |
     | Pull Request
     |
     v

    main

------------------------------------------------------------------------

# Production

Production не является веткой.

Production --- это запущенный экземпляр приложения.

Например:

Git:

    main

    ●──●──●──●
            |
          v0.5.0

Сервер:

    World Engine
    version v0.5.0

То есть:

Production = конкретный release, который сейчас запущен.

------------------------------------------------------------------------

# Deployment

Процесс выпуска:

    main
     |
     |
     create tag
     |
     v
    v0.5.0
     |
     |
     deploy
     |
     v
    Production

Например:

    git tag -a v0.5.0 -m "Release v0.5.0"
    git push origin v0.5.0

------------------------------------------------------------------------

# Почему не нужна постоянная stable ветка

Изначальная идея:

    dev
     |
    main
     |
    stable
     |
    server

Но отдельная stable ветка создаёт дублирование.

Лучше:

    dev
     |
    main
     |
    v0.5.0
     |
    production

Роль stable выполняет release tag.

------------------------------------------------------------------------

# Rollback

Если production сломан:

Не нужно откатывать main.

Пример:

    production:

    v0.5.0

Проблема.

Возвращаем:

    production:

    v0.4.0

Git история остаётся:

    main

    ●──●──●──●──●
          |
        v0.4.0

              |
            v0.5.0

------------------------------------------------------------------------

# Docker и версии

Рекомендуется связывать релизы с Docker images.

Пример:

    world-engine:v0.4.0
    world-engine:v0.5.0

Production запускает:

    world-engine:v0.5.0

При проблеме:

    world-engine:v0.4.0

------------------------------------------------------------------------

# GitHub Releases

Каждый значимый релиз должен иметь:

-   tag;
-   changelog;
-   описание изменений;
-   инструкции миграции;
-   ссылки на документацию.

Пример:

    Release v0.5.0

    New:
    - Project cloning
    - Template transfer

    Fixed:
    - Asset import bugs

------------------------------------------------------------------------

# Коммиты

Рекомендуемый стиль:

    feat:
    fix:
    refactor:
    docs:
    test:
    chore:
    perf:

Примеры:

    feat: add project templates

    fix: prevent duplicate asset IDs

    refactor: move storage to repository layer

    docs: update architecture documentation

------------------------------------------------------------------------

# Pull Request процесс

Для важных изменений:

1.  Создать feature branch.
2.  Реализовать изменение.
3.  Добавить тесты.
4.  Создать Pull Request.
5.  Проверить код.
6.  Merge в dev.
7.  После стабилизации merge в main.

------------------------------------------------------------------------

# Тестирование

Перед попаданием в main:

Обязательно:

-   unit tests;
-   сборка проекта;
-   проверка типов;
-   линтер;
-   отсутствие критических warning.

Перед production:

-   полный тестовый запуск;
-   проверка миграций;
-   проверка импорта/экспорта;
-   проверка обратной совместимости.

------------------------------------------------------------------------

# Рекомендуемый жизненный цикл версии

Пример:

## Разработка

    feature/new-block
            |
            v
           dev

## Стабилизация

    dev
     |
     v
    main

## Выпуск

    main
     |
     v
    v0.6.0

## Production

    server
     |
     v
    World Engine v0.6.0

------------------------------------------------------------------------

# Итоговая модель

                        GitHub

    feature/*
        |
        v

       dev
        |
        |
        v

      main
        |
        |
        v

     release tag
       v0.x.x
        |
        |
        v

    Production Server
       |
    World Engine
    version v0.x.x

Главное правило:

-   ветки используются для разработки;
-   tags используются для версий;
-   production использует конкретный release;
-   стабильность достигается процессом, а не отдельной веткой.
